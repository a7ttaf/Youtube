## Deviations from the Phase 6 checklist

Three deliberate divergences from the Phase 6 checklist in the S2 plan;
all recorded here so the next reviewer understands them.

1. **Marker set.** The Phase 6 checklist uses `✅ shipped` / `⚠️ partial`
   text labels. The feedback memory rule (saved 2026-05-22, after the
   Phase 6 plan was written) is more specific:
   `✅ PR #N`, `⏳ PR #N — remaining: <note>`,
   `🗑️ removed in PR #N — <reason>`. The memory rule is the more recent
   and more useful guidance (it forces the writer to name the
   contributing PR and the concrete remaining work), so this PR uses the
   memory rule.
2. **Phase numbering.** Step 8 of the checklist instructed: "Delete the
   entire `## Phase 6 — Neo4j graph read-model` section and replace with
   `## Phase 6 — Multi-tenant foundation (S2)`". That instruction was
   authored when `01_IMPLEMENTATION_PLAN.md` still had a Neo4j Phase 6.
   In the current doc, Phase 6 is already "Export center" (the Neo4j
   section was removed in an earlier pass). Rather than renaming Phase 6
   to multi-tenant — which would hide the still-valid Export center
   deliverable behind an infrastructure label — this PR places
   multi-tenant work in a clearly-labeled
   `## Cross-cutting infrastructure (Sx — 2026-05-10 → 2026-05-21)`
   section before Phase 0. The product phase numbering 0–7 stays intact
   and accurate.
3. **Honesty over plan optimism.** The Phase 6 checklist's example
   marker mapping called items like "Channel registry. ✅ shipped",
   "Monthly revenue normalization. ✅ shipped", and "AdSense payment
   sync. ✅ shipped" when in fact only the ORM models, repositories, and
   unit tests exist — no real ingestion, no real revenue normalization
   pass, no real AdSense pull. This PR marks those
   `⏳ — remaining: <concrete missing piece>`. Calling scaffolding
   "shipped" is exactly the drift that caused this Phase 6
   reconciliation in the first place.

## Follow-ups identified during reconciliation

These are written down here rather than added as planning bullets so the
operator can decide which become next-spec candidates:

1. **S3 spec — tenant hardening at storage layer.** `Docs/17` specifies
   RLS + Postgres GUC + composite FKs + tenant-scoped unique keys +
   `app_tenant` / `app_platform` roles. None implemented. The S2 merge
   gives end-to-end tenant context in application code, but the
   database is not yet defending itself; any future PR that bypasses
   repository methods (raw SQL, bulk migration script, third-party ETL
   tool) could leak across tenants.
2. **Multi-currency engine spec.** `Docs/18` specifies paired
   `amount_native` + `fx_rates` table; only `currency_exchange_rates`
   scaffolding exists. No rate fetcher, no fallback policy. Finance
   work in P2 depends on this.
3. **Frontend tenant header + dashboard pages spec.** The S2 integration
   spec's Phase 5 ("Frontend tenant header") is still open. The React
   shell (PR #10) has no API client and no `X-UMS-Tenant` header
   injection. Backend is ready for it.
4. **Real ingestion connectors spec.** Master Plan Phases 2 (YouTube)
   and 3 (AdSense) are `⏳` across the board because credential
   scaffolding exists but no real pulls run. This is the single largest
   gap between doc-claimed state and reality.
